## 构建和核对

在项目目录运行：

```powershell
uv sync
uv run --no-sync python -m unittest discover -s tests -p "test_[ps]*.py" -v
uv build --no-sources
uv run --no-sync python scripts/verify_distribution.py dist
```

构建产生 wheel 和源码包。两者只包含屏控及示例图片资源；不包含 `gem12_touch`、触控示例、诊断日志或本地参考资料。不要混用不同版本的 `dist` 文件；验证脚本要求目录内只有本次版本的两个发行文件。

升级版本时同步修改 `pyproject.toml` 和锁文件，GitHub Release 标签采用 `v<版本>`，例如首个版本 `v0.1.0`。不要使用同一版本号上传修改过的发行内容。

## 配置 Trusted Publishing

推荐使用 GitHub Actions 的 Trusted Publishing，不在仓库保存 PyPI token。已提供工作流 `.github/workflows/publish.yml`。

| 设置 | PyPI | TestPyPI |
|---|---|---|
| 项目名 | `gem12-screen` | `gem12-screen` |
| GitHub owner | `hanselu` | `hanselu` |
| Repository | `gem12-screen` | `gem12-screen` |
| Workflow filename | `publish.yml` | `publish.yml` |
| Environment | `pypi` | `testpypi` |

尚不存在的项目可在账号的 Publishing 页面添加 pending publisher。该配置不会预先占用包名；首次成功上传才创建项目。TestPyPI 使用独立账号和发布配置。

在 GitHub 仓库创建对应的 `pypi`、`testpypi` environment，然后按上表在相应平台设置 publisher。配置前应先确认 owner、仓库及工作流名称与实际提交一致。

工作流行为：

1. 在 Windows、Linux、macOS 上运行无硬件访问的屏控测试。它们不是这三个系统的真机显示验收。
2. 构建发行包、核对内容、在隔离环境中安装 wheel 并检查公开导入和命令行帮助。
3. 手动运行工作流时，默认目标为 TestPyPI，也可明确选择 PyPI。
4. 发布 GitHub Release 时上传 PyPI，并检查标签和包版本一致。普通提交或推送不会触发上传。

后续版本建议先手动选择 TestPyPI 验证，再进行正式发布。本地技术检查不能替代真实的 GitHub Actions、OIDC 认证或上传验证。

## 其他项目安装

在调用项目中安装已发布版本：

```powershell
uv add "gem12-screen==0.1.0"
```

普通虚拟环境也可使用 `pip install gem12-screen==0.1.0`。代码统一通过[屏幕公共接口](屏幕公共接口.md)调用，业务项目不复制库源码。

本地联调可使用：

```powershell
uv add "gem12-screen @ E:/Project/gem12_screen"
```

通过 GitHub 复用已发布标签时，可指定：

```powershell
uv add "gem12-screen @ git+https://github.com/hanselu/gem12-screen.git@v0.1.0"
```

远程仓库已有 `v0.1.0` 标签。后续版本需使用实际存在的对应标签。
