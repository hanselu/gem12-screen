# 轻触通知中断与退出耗时诊断

日期：2026-10-09。

当前结论：完整用户日志已确认第 16 次后没有新的 Windows 回调，约 10 秒等待发生在关闭会话时。后续修正了会话初始化前使用旧设备编号的缺口，原始通知中断根因仍未确认。以下按诊断阶段保留证据。

## 用户报告与当前判断

用户运行 `examples/listen_touch.py`，正常收到 7 次通知，其中第 7 次按住约 2～3 秒。随后无论轻触还是长按都不再打印通知；按 Ctrl+C 后等待约 10 秒才退出。

原始通知时间依次为 9493.765、9496.468、9497.375、9497.859、9498.296、9499.656、9500.562 秒。相邻通知间隔为 2.703、0.907、0.484、0.437、1.360、0.906 秒。通知时间不是每次物理按下／松开的时间。

这个报告不能仅用“无法区分长按与轻触”或“接触位置不好”解释。需要分别检查系统是否停止回调、回调是否阻塞以及 Python 是否收到通知却没有输出。原示例未记录这些信息，因此无法从这份日志确定是哪一层发生问题。

## 本次真机诊断

临时诊断使用正式 `FingerprintTouch`，在内存中记录每次原始回调、对外读取及回调耗时；在调用线程中记录枚举、打开、注册、注销、关闭的耗时及返回状态。未在系统回调中写文件或打印日志。

### 分阶段实验

1. 空白基线：连接后立即注销及关闭，注销耗时 0.000131 秒，关闭耗时 0.002146 秒。
2. 用户确认完成 2 次居中轻触，收到 2 次系统回调和 2 个对外通知。
3. 用户确认完成 1 次约 3 秒长按并放开，收到 1 次回调和 1 个通知。
4. 用户确认再完成 2 次居中轻触，收到 2 次回调和 2 个通知，未发生通知中断。
5. 正常停止：注销耗时 0.000190 秒，关闭耗时 0.046024 秒，两步均为 `0x00000000`。

这次阶段之间有较长的提示和反馈等待，不等于用户原来连续操作的节奏。

### 连续序列实验

请用户连续轻触 6 次、间隔约 0.5～1 秒，第 7 次按住约 2～3 秒后放开，等约 2 秒后再轻触 2 次。用户确认完成，共收到 9 次回调和 9 个通知，无错误或拒绝信息。

前 7 个通知实际间隔约 1.7～2.2 秒，比用户原日志中的部分间隔更长。没有同步记录物理按下和松开，不能确认复现了完全相同的动作节奏，也不能直接从通知间隔推断驱动行为。停止时注销耗时 0.000249 秒，关闭耗时 0.045514 秒，两步均为 `0x00000000`。

这两轮没有复现通知中断或约 10 秒退出，不能判定用户报告的问题已经修复。原始数据见[轻触通知中断与退出诊断数据.json](轻触通知中断与退出诊断数据.json)。随后用户提供了更完整的异常日志，进一步结果见下文。

## 代码改进

- 示例在收到 Ctrl+C 后、进入清理前立即打印“正在关闭监听”，成功清理后才打印“监听已关闭”。关闭过程中再次被中断时明确报告清理状态未确认。
- 新增 `--debug` 诊断模式，在调用线程打印系统回调进入／结束的累计计数、读取通知及错误、注销监听和关闭会话各自的开始提示、耗时和 HRESULT。
- 系统回调中仅增加计数，不打印日志。某次读取时“进入”暂时比“结束”多一次可能只是回调仍在完成；应结合连续记录判断，不以单条日志认定阻塞。
- 没有加入无通知时自动重连、自动取消或停止系统服务的逻辑，因为普通空闲也没有通知，目前无法据此确定故障。屏控代码未修改。

复现时运行：

```powershell
uv run python examples/listen_touch.py --debug
```

如果再次中断，应保留最后一次成功通知到 Ctrl+C 清理完成的输出：回调计数是否停止增加、进入与结束计数是否长期不一致、注销或关闭哪个步骤耗时约 10 秒，可用来缩小问题范围。诊断日志反映本程序收到的回调，不能直接区分传感器、驱动和 Windows 服务内部的原因。

26 项自动测试通过，含回调计数与分步清理日志、关闭前提示顺序、清理被中断时不误报成功的新测试。没有真机复现约 10 秒阻塞，所以这些改动改善了可观察性，没有宣称消除了底层中断。

## 清理和接口依据

本次在开始真机诊断前再次以沙箱外只读查询确认 `WbioSrvc` 为 Stopped、Automatic。结束后在沙箱外重新核对，服务已经处于 Stopped、Automatic，因此没有手动停止服务、没有弹出管理员确认或修改启动配置。临时诊断文件已清理，未提交代码。

[WinBioCloseSession](https://learn.microsoft.com/en-us/windows/win32/api/winbio/nf-winbio-winbioclosesession) 的同步调用会阻塞到操作完成或出错，文档没有保证固定退出耗时。本程序使用这种同步会话；最初两轮没有复现约 10 秒等待，下文记录了随后用户日志和恢复实验中捕获的等待。

## 后续：第 16 次后停止通知的完整日志

用户提供了[完整日志](轻触通知停止用户日志.txt)，最后一次触碰是否长按未知，不能再假定异常仅由长按引起。

- 第 16 次成功通知：02:06:04.748，Unit ID 3，RejectDetail 0，回调进入／结束计数均为 16。
- 此后 21 次等待超时仍为 16／16，最后一次为 02:06:15.261，期间没有新的系统回调进入本程序。
- Ctrl+C 后注销监听成功，接口报告耗时 0.000 秒。
- 随后的 `WinBioCloseSession` 成功，但耗时 10.016 秒，明确定位了退出等待所在的调用。

因此，此次停止通知不是 Python 已收到新事件却没有打印，也没有回调停留在本程序内部的迹象；缺失发生在新的 Windows 回调抵达之前。仍不能区分设备、驱动、生物识别服务或系统事件分发的原因。

对应 Windows Biometrics Operational 日志仅有初始化事件，包含安全组件不可用 `0x80070032`、原因 76 的信息及传感器创建记录，没有直接解释停止通知的条目。该安全组件信息出现在前 16 次正常通知之前，不能仅凭它判定异常原因。

### 取消与重连实验

先按用户原来的方式进行约 20 次混合接触，包含长按、短按和密集短按，记录到 14 个成功通知。再确认 3 次居中轻触，新增 2 个通知，总数为 16；不能把这些计数直接等同于已确认完全停止，或推断固定的 16 次上限。

调用 `WinBioCancel` 返回成功，耗时 0.000207 秒，随后读出 `0x80098004`（`WINBIO_E_CANCELED`）通知。这表示取消被执行，不表示触摸监听已经恢复。随后注销成功，但关闭会话仍耗时 9.999562 秒，重新打开耗时 16.887866 秒。因此没有将取消调用加入正式关闭逻辑，也没有承诺重连立即完成。

重连后用户完成 3 次轻触，回调计数为 3／3，但没有读出触摸通知。该段实验未采集回调原始类型及设备编号，所以不能确认具体被忽略的原因。

随后重新启动带原始回调诊断的探针：目标枚举编号已变成 4。用户完成 3 次轻触，原始回调均为类型 1、状态成功、Unit ID 4、RejectDetail 0，均正常读出。Windows 日志还记录了同一 Microarray 设备的重新创建。编号变化是已观察事实，但不能据此确认之前缺失回调的根因。

实验原始结果见[轻触恢复与编号验证数据.json](轻触恢复与编号验证数据.json)。

### 连接顺序修正

原代码先枚举目标编号，再调用 `WinBioOpenSession`。如果打开会话期间 Windows 初始化或重建设备，枚举得到的编号可能过期，后续通知可能被目标过滤逻辑忽略。

现改为先打开会话，再枚举目标编号，最后注册回调；枚举失败也会关闭已打开的会话。新增诊断字段记录最近被忽略的设备编号，仍保留目标设备过滤，不自动接受其他设备的输入。

新增回归测试模拟打开会话时编号从 3 变成 4：修正前失败（仍保存 3），修正后通过且能读到编号 4 的通知。全部 27 项测试通过，修正后的正式接口真机连接、读取空队列、关闭检查成功，选定 Unit ID 4。该改动修正的是初始化编号时序缺口，不宣称解决了“系统不再回调”的原始问题。

本轮真机测试前、后均核对 `WbioSrvc` 为 Running、Automatic，未手动停止或重启服务，未更改驱动或设备，也未连接屏幕。临时探针已清理，正式修改未提交。
